# 朱批 v2 基础审批重构计划

> 本文是给后续 agent 使用的可执行改造说明。目标不是继续修补旧朱批链路，而是把朱批语义收敛为一个最小、稳定、可验证的基础审批功能。
>
> 核心要求：**只保留基础审批：皇帝批准后，流程才能继续推进。去掉封还/驳回分支，不再让人类在 agent loop 中反复参与。**

---

## 0. 目标与非目标

### 0.1 目标

1. **只审批 `revw` 文档**
   - 人类只看门下侍中的审查报告 `revw_*`。
   - `plan`、`dsgn`、`pdsg` 等不再进入朱批队列。

2. **只保留“准奏 / approved”**
   - 前端不再显示“封还”按钮。
   - 后端审批接口不再接受 `rejected`。
   - 审批状态机只保留：`in_review -> approved`。

3. **皇帝批准后才能继续流程**
   - Pipeline 的 `approval_gate` 必须等对应 `revw_*` 为 `approved` 后才能推进。
   - 工具门禁必须阻止下游引用未批准的 `revw_*`。

4. **减少人类 loop 参与**
   - 不再通过“封还 -> agent 修改 -> 再批”的长链处理不满意场景。
   - 人类如果不满意审查结果，应暂停当前 loop，回滚到上一次文档状态/检查点，然后重新下命令。

### 0.2 非目标

本轮不要实现以下内容：

- 不做复杂驳回流转。
- 不做“修改意见 -> 自动返工 -> 再提交”的审批闭环。
- 不引入新的多状态审批模型。
- 不保留自动批准 / auto approve 作为默认流程的一部分。
- 不扩大审批范围到 `plan`、`dsgn`、`pdsg`。

## 1. 新朱批语义

### 1.1 唯一审批对象

`MUST_APPROVE_TYPES` 应改为只包含：

```rust
pub(super) const MUST_APPROVE_TYPES: &[&str] = &["revw"];
```

含义：

| 文档类型 | 是否朱批 | 说明 |
|---|---:|---|
| `revw` | 是 | 门下侍中的审查报告，是唯一人类审批入口 |
| `plan` | 否 | 中书令内部计划/阶段规划，不再待批 |
| `dsgn` / `pdsg` / `ddtl` | 否 | agent 内部设计与执行资料 |
| `task` / `reqs` / `anls` / `ctrt` / `rprt` | 否 | 普通工作文档 |

### 1.2 状态机

审批状态机只保留两态：

```text
revw created/ready -> in_review -> approved
```

规则：

1. `revw` 进入 `in_review` 后，前端显示“待陛下朱批”。
2. 皇帝点击“准奏”后，后端写入 `status: approved`。
3. `approval_gate` 只有在 `revw.status == "approved"` 时才能通过。
4. 已批准的 `revw` 如果被修改，应重新变为 `in_review`，需要再次准奏。
5. 不再产生 `status: rejected`。

### 1.3 不满意时的产品路径

不满意审查结果时，不走封还状态。

推荐用户路径：

1. 用户暂停当前 loop。
2. 用户恢复到上一检查点或上一文档状态。
3. 用户重新下命令，要求 agent 重新设计/审查。

因此本轮只需要保证基础审批可靠，不需要实现“封还”闭环。

## 2. 后端改造

### 2.1 `parse.rs`：只审批 `revw`

文件：

- `shuji-app/src-tauri/src/tool/documents/parse.rs`

修改：

```rust
pub(super) const MUST_APPROVE_TYPES: &[&str] = &["revw"];
```

验收：

- `plan` 不再被视为 must-approve。
- `revw` 仍会被扫描为待批文档。

### 2.2 `crud.rs`：只有 `revw` 创建时进入待批

文件：

- `shuji-app/src-tauri/src/tool/documents/crud.rs`

当前逻辑里 `plan | revw` 都会设置 `status: in_review`。需要改为只处理 `revw`：

```rust
let status = match doc_type.as_str() {
    "revw" => "in_review".to_string(),
    _ => String::new(),
};
```

保留：

- `revw` 创建后仍可写入 pending cache。
- 已批准 `revw` 被修改后仍应回到 `in_review`。

注意：

- 如果后续要避免空壳 `revw` 过早进入待批，可以再做“首次 append 后入队”。本轮不是必须项，除非现有测试或体验明确需要。

### 2.3 `approval.rs`：删除 rejected 分支

文件：

- `shuji-app/src-tauri/src/tool/documents/approval.rs`

需要修改：

1. `tool_set_document_status` 只接受 `approved`：

```rust
if new_status != "approved" {
    return ToolOutput::error(
        "set_document_status",
        id,
        "invalid_status",
        "status must be approved",
    );
}
```

2. 删除或停用 `rejected` 相关逻辑：
   - 不再写 `status: rejected`。
   - 不再生成 `朱批[rejected ...]`。
   - 不再在审计中写 `status=rejected`。

3. `check_must_approve_status` 不再检查 `rejected`：
   - 未批准只关心 `in_review`。
   - 如果历史文档里仍有 `rejected`，建议当作“未批准/不可推进”处理，错误信息提示用户重新生成审查报告。

推荐兼容处理：

```rust
if ref_meta.status == "in_review" || ref_meta.status == "rejected" {
    return Err(format!(
        "Document {} references {}, which is not approved yet. Please approve the review document before proceeding.",
        subject_doc_id, doc_id
    ));
}
```

这样旧 `rejected` 文档不会绕过门禁，但不会继续暴露封还语义。

4. `set_document_status_tool_def` 的 schema 只保留：

```json
"enum": ["approved"]
```

描述改为：

```text
Approve a review document. Only revw documents can be approved.
```

### 2.4 `dispatch.rs`：审批状态只允许 approved

文件：

- `shuji-app/src-tauri/src/tool/dispatch.rs`

当前 `set_document_status` 分支允许 `approved | rejected`。改为只允许 `approved`。

错误文案改为：

```text
状态值不合法：必须是 approved。
```

### 2.5 `commands/workflow/audit.rs`：Tauri 命令只接受 approved

文件：

- `shuji-app/src-tauri/src/commands/workflow/audit.rs`

`set_document_status` 命令可以暂时保留 `status: String` 参数以减少前端 API 改动，但后端应拒绝非 `approved`。

后续可选优化：

- 新增 `approve_document(id, emperor_note)` 命令替代通用 `set_document_status`。
- 当前阶段不要求改命令名，避免大范围前后端联动。

## 3. Pipeline 改造

### 3.1 `approval_doc_from_upstream` 只认 `revw`

文件：

- `shuji-app/src-tauri/src/pipeline/artifacts.rs`

当前逻辑优先 `revw` / `plan`，再 fallback 到任意文档。v2 必须收紧：

```rust
pub fn approval_doc_from_upstream(
    artifacts: &HashMap<String, String>,
    depends_on: &[String],
) -> Option<String> {
    collect_upstream_doc_ids(artifacts, depends_on)
        .into_iter()
        .find(|id| id.starts_with("revw_"))
}
```

原因：

- `approval_gate` 是人类审批点，必须绑定门下审查报告。
- 如果没有 `revw_*`，说明流程设计错误，应暴露错误，而不是误批 `dsgn` / `plan`。

### 3.2 `approval_gate` 无 `revw` 时应阻塞并给出明确错误

文件：

- `shuji-app/src-tauri/src/pipeline/engine.rs`

当前 `approval_gate` 找不到文档时会返回空 `doc_id` 的 `AwaitingApproval`。建议改为失败或等待内阁修复，但必须提示清楚：

```text
approval_gate requires an upstream revw document, but none was found.
```

推荐行为：

- 如果 `approval_gate` 没有上游 `revw_*`，返回 `StepFailed`，`on_failure` 按计划处理。
- 不要让 UI 展示空文档审批。

### 3.3 `resume_with_input` 只验证 `revw approved`

文件：

- `shuji-app/src-tauri/src/pipeline/engine.rs`

manual 模式下恢复 `approval_gate` 时：

1. 找上游 `revw_*`。
2. 如果没有 `revw_*`：阻塞/失败。
3. 如果 `status != approved`：继续 `AwaitingApproval`。
4. 只有 `status == approved`：标记 gate done 并继续。

## 4. 内阁与自动审批改造

### 4.1 去掉 must-approve 自动批准逻辑

文件：

- `shuji-app/src-tauri/src/agent/neige/mod.rs`

目标：

- 不再由内阁自动批准文档。
- 不再在 pending 后连续重试并调用 `tool_set_document_status(auto=true)`。
- 不再要求内阁必须调用 `request_decision` 才能进入审批。

建议改法：

1. 删除或禁用以下逻辑：
   - `must_approve_retries`
   - `ApprovalMode::Auto` 自动批准分支
   - 注入 “Please immediately call request_decision” 的强制循环

2. 保留简化版 pause：

```rust
let has_pending = crate::tool::documents::get_first_pending_approval(&working_dir).await.is_some();
let should_pause = has_pending && route.is_none();
```

或者如果 Pipeline 已处于 `AwaitingApproval`，则让 Pipeline 负责暂停，内阁不要重复暂停。

### 4.2 配置项处理

文件：

- `shuji-app/src-tauri/src/config/mod.rs`
- `shuji-app/src-tauri/config.toml`
- `shuji-app/src-tauri/config.local.toml`（运行时）

当前有 `approval.mode = manual|auto` 与 `auto_retries`。v2 基础审批不需要自动批准。

推荐处理：

- 短期：保留配置结构，忽略 `auto`，内部强制 manual 行为。
- 中期：移除 `ApprovalMode::Auto` 与 `auto_retries`，设置页同步删除。

本轮实施建议采用短期方案，减少配置迁移风险。

### 4.3 Prompt 更新

文件：

- `shuji-app/src-tauri/src/agent/neige/prompt.md`
- `shuji-app/src-tauri/src/agent/neige/levels/level*.md`
- `shuji-app/src-tauri/src/agent/menxiashizhong/prompt.md`
- `shuji-app/src-tauri/src/agent/menxiashizhong/skills/*.md`

需要统一文案：

- 皇帝只审批 `revw` 审查报告。
- `plan` 不需要朱批。
- 门下侍中必须创建 `revw`，并让 `revw` 清楚表达：
  - 审查结论
  - 是否建议继续
  - 主要风险
  - 引用的设计/计划文档
- 不再要求“封还”或“请求修改意见”。
- 若皇帝不满意，操作路径是暂停、回滚、重新下命令。

## 9. 风险与校准

### 9.1 `revw` 质量成为关键

人类只看 `revw`，所以门下审查报告必须足够结构化。若后续发现准奏过于盲目，应优先优化门下 prompt，而不是把审批范围重新扩大到 `plan`。

门下 `revw` 至少应包含：

- 审查结论：建议准奏 / 不建议继续
- 关键风险
- 依据文档 ID
- 必须修复项
- 可接受的残余风险

### 9.2 旧 `rejected` 文档兼容

历史项目中可能已有 `status: rejected`。v2 不再创建 rejected，但门禁不能让旧 rejected 绕过。

建议：

- `rejected` 在门禁中视为未批准。
- UI 不提供创建 rejected 的入口。
- 不做自动迁移，避免破坏历史审计。

### 9.3 自动审批配置兼容

如果短期不删除设置页中的 auto mode，后端也必须忽略自动放行，确保“皇帝审批完后才能推进流程”成立。

最终目标是移除 auto approve UI 与配置，但可以分后续 PR 完成。

## 10. 最终验收标准

完成后系统必须满足：

1. `plan` 不再触发待批，不阻塞流程。
2. 只有 `revw` 可以进入 `in_review`。
3. 前端只显示“准奏”，没有“封还”。
4. 后端拒绝 `set_document_status(..., "rejected")`。
5. `approval_gate` 只能等待并验证 `revw_*`。
6. 未批准的 `revw` 会阻止流程推进。
7. 批准后的 `revw` 允许流程继续。
8. 内阁不会自动批准文档。
9. `pending_approvals.json` 不是审批真相源，删除后可由扫描恢复。
10. 后端 `document_test`、`pipeline_test` 和前端 `DocPreview.test.tsx` 均覆盖新语义。
