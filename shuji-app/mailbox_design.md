# 信箱机制消息流转图（完整版 V2）

## 核心规则

1. **Pull 式**：调度器轮询各部门信箱，有新消息才调 LLM
2. **发送方路由**：每个 LLM 输出通过 `<route>` 标签声明目标部门 + 优先级
3. **两个信箱**：每个部门有 快信箱（更短 pull 周期，用于紧急/皇帝指令）和 慢信箱（常规消息）
4. **内阁 = 皇帝的门面**：所有皇帝看到的消息由内阁产出，所有皇帝输入投到内阁快信箱
5. **消息先消费再投递**：处理完当前消息后，把产出投到目标信箱
6. **每次 tool-call 迭代前查快信箱**：对于 tool-use 部门（中书省、工部、尚書省），每次工具调用前检查快信箱，发现中断指令立即停止；对于纯文本部门，发起前和完成路由前各查一次

---

## 信箱结构

```
每个部门：
  ├─ 快信箱（Fast: 高优先级，短pull周期，用于皇帝指令/紧急阻断）
  └─ 慢信箱（Slow: 常规消息，长pull周期）

特殊：
  内阁快信箱 ← 皇帝所有输入 + 各部门紧急上报
  内阁慢信箱 ← 各部门日常状态更新（定期汇总）
  户部信箱  ← 各部门 token 报告（外部门向户部发）
  制司信箱  ← 独立周期，不依赖执行流水线
```

---

## 消息结构

```json
{
  "id": "uuid",
  "from": "门下省",
  "to": "中书省",
  "priority": "fast|slow",
  "subject": "审查驳回：方案缺少API定义",
  "body": "驳回理由...",
  "attachments": [              // 附带上下文
    {"type": "design", "path": ".shuji/designs/overall_design.md"},
    {"type": "review", "path": ".shuji/reviews/review_overall.md"}
  ],
  "hop_count": 0,
  "in_reply_to": "前一条消息ID"  // 用于追踪对话链
}
```

## 完整流转

### 第一轮：需求接收

```
皇帝输入"做个博客系统"
  ↓ 投递
内阁快信箱 ← {from:皇帝, body:"做个博客系统", priority:fast}
  ↓ 内阁 pull
内阁 LLM → 判断是项目需求
  ↓ 路由
中书省慢信箱 ← {from:内阁, body:"皇帝需求：做个博客系统，请设计方案", priority:slow}
```

---

### 第二轮：整体方案设计（含澄清循环）

```
中书省 pull（慢信箱）
  ↓
中书省 LLM tool-use
  ├─ 有疑问需要澄清：
  │   路由→ 内阁快信箱 ← {from:中书省, body:"需要确认……", priority:fast}
  │     ↓ 内阁 pull
  │    内阁呈报皇帝 → 皇帝回答
  │    内阁快信箱 ← {from:皇帝, answer:"用Python"}
  │    内阁判断：这是对中书省问题的回答
  │    路由→ 中书省快信箱 ← {from:内阁, body:"皇帝回答：用Python", priority:fast}
  │     ↓ 中书省下次pull（快信箱优先）
  │    继续设计（附带皇帝回答）
  │
  └─ 方案完成：
      路由→ 门下省慢信箱 ← {from:中书省, body:设计方案, priority:slow}
```

**快信箱覆盖规则**：中书省 pull 到慢信箱"设计方案" → 开始执行 LLM → LLM 跑完 → 提交前检查快信箱
- 快信箱有"皇帝回答了问题" → 把回答合并到上下文，重新设计
- 快信箱有"停止重做" → 废弃本次产出，执行新指令
- 无指令 → 提交设计

---

### 第三轮：方案审查

```
门下省 pull（慢信箱）→ 审查方案
  ├─ 通过：
  │   路由→ 内阁快信箱 ← {from:门下省, body:审查报告, priority:fast}
  │     ↓ 内阁 pull
  │    内阁 LLM 汇总方案+审查报告 → 呈报皇帝（附选项 A/B/C）
  │
  └─ 驳回：
        ├→ 中书省慢信箱 ← {from:门下省, body:"驳回原因……，请修改", priority:slow}
        │    （中书省正常拉取后重做）
        └→ 内阁慢信箱 ← {from:门下省, body:"我驳回了方案，原因：……", priority:slow}
             （内阁知悉，不呈报皇帝，除非后续升级）

驳回≥4次 → 升级：
  内阁快信箱 ← {from:调度器, body:"方案已驳回4次，需皇帝强制定夺", priority:fast}
    ↓ 内阁 pull
  内阁 LLM 汇总 4 次驳回历史 → 呈报皇帝（附选项 A通过 / C终止）
```

---

### 第四轮：皇帝否决驳回（冲突处理）

```
场景：门下省驳回 → 中书省已在修改 → 皇帝说"原方案通过"

皇帝输入"原方案不错，通过" → 内阁快信箱
  ↓ 内阁 pull
内阁判断：这是否决驳回
  ├→ 中书省快信箱 ← {from:内阁, body:"停止修改，皇帝批准了原方案，原方案有效", priority:fast}
  └→ 门下省快信箱 ← {from:内阁, body:"皇帝命汝通过，立刻签署原方案", priority:fast}

中书省正在跑 tool-call 循环：
  └→ 第 N 次 tool-call 前 → 检查快信箱
       ├─ 发现"停止修改"指令 → 立即中止循环，废弃已产出内容
       │   回复调度器：按皇帝旨意执行
       └─ 无指令 → 继续下一次 tool-call

门下省 pull（快信箱）→ 收到"皇帝命汝通过"
  ↓ 直接签署原方案 → 路由→ 内阁快信箱（重新走批准流程）
```

关键：**不中断 LLM，但提交前检查快信箱决定去留。**

---

### 第五轮：尚書省执行

```
内阁呈报 → 皇帝批示 A（批准）
  ↓ 内阁投递
尚书省快信箱 ← {from:内阁, body:执行令+方案+审查报告, priority:fast}

尚书省 pull → LLM tool-use dispatch（内部固定流程 + 循环）：
  1. 发文→ 吏部 → 拆解任务
  2. 发文→ 兵部 → 编写测试用例
  3. 发文→ 工部 → 根据测试用例编码
  4. 发文→ 兵部 → 运行测试
       ├─ 不通过 → 循环到第 3 步（工部修→兵部测）
       └─ 通过 → 继续
  5. 发文→ 刑部 → 异常检查
       ├─ 不通过 → 循环到第 3 步（工部修→兵部测→刑部检）
       └─ 通过 → 继续
  6. 发文→ 礼部 → 规范检查
       ├─ 不通过 → 循环到第 3 步
       └─ 通过 → 继续
  7. 发文→ 户部 → 记录归档
       ↓
  8. 路由→ 内阁慢信箱 ← {phase:1, status:"执行完成", priority:slow}
```

说明：
- 尚书省内部是固定的 tool-call 循环，不需信箱
- 刑部/兵部/礼部发现严重问题时，跳过内部循环直接：
  `→ 内阁快信箱 ← {from:刑部, body:"发现严重Bug：……", priority:urgent}`
- 各步骤状态更新 → 内阁慢信箱（汇总用）

---

### 第六轮：并行阶段

```
尚书省执行阶段1 → 内阁慢信箱（阶段1完成）
  ↓
内阁汇总时发现阶段1已完成,阶段2开始条件满足 → 投递阶段2执行令
  ↓
尚书省快信箱 ← 阶段2执行令（同理阶段3...）

* 阶段并行由内阁判断"下一阶段条件是否满足"后投递执行令
* 当前设计：前一阶段执行完成 → 内阁汇总通知 → 下一阶段开始
```

---

### 第七轮：日常汇总

```
内阁（慢信箱 pull 周期到）：
  信箱里积压了：
  - 兵部 "阶段1测试通过"
  - 工部 "阶段1编码完成"
  - 刑部 "阶段1检查通过"
  - 制司 "审计无异常"
  - 户部 "token 报告"

内阁 LLM 汇总 → 呈报皇帝：
  "项目进度：阶段1已完成60%，工部编码中，刑部已通过。
   当前无阻塞，一切正常。
   详细日志：.shuji/logs/..."
  （不带选项，不阻塞，纯参考）
```

---

### 第八轮：制司独立审计

```
制司独立 pull（固定周期）：
  ├─ 审查各日志 → 无异常 → 内阁慢信箱（routine）
  └─ 发现问题 → 内阁快信箱（urgent）
       ↓
      内阁呈报皇帝 → 皇帝决策
```

## 去重与防环

| 机制 | 做法 |
|------|------|
| 消息 ID | 每条消息 uuid，消费后标记已读 |
| hop_count | 超过 20 跳 → 强制投递到内阁快信箱 |
| 快信箱优先 | pull 时先消费快信箱所有消息，再消费慢信箱 |
| 内阁合并 | 短时间内同主题多次消息，内阁合并呈报 |
| tool-call 间隙查快信箱 | tool-use 部门每次工具调用前检查快信箱，发现中断指令立即中止 |
