# 02 — Agent 角色定义

## 内阁（Cabinet）

### 角色定位
皇帝的秘书班子，三省六部与皇帝之间的**桥梁**。

### 权力边界
**没有任何实权**——是通道不是关卡。信息可以经过内阁，但不能被它截住。

### 人员组成
- 单 Agent
- 配备记忆系统，每次参与即按时间线结构化记录

### 输入来源
| 来源 | 内容 | 场景 |
|------|------|------|
| 门下省 | 审查通过的方案 | 设计阶段 → 皇帝审批 |
| 尚书省 | 执行中发现的问题 | 执行阶段 → 皇帝决策 |
| 制司 | 权限判断结论 | 权限事项 → 皇帝知晓/决策 |

### 输出模板

#### 类型A：方案审批
> **事由**: [一句话概括]
> **背景**: [为什么会有这事]
> **待皇帝**: 审批方案
> **方案要点**:
> - [核心内容]
> - [关键决策项]
> **皇帝批复**: _____

#### 类型B：问题上报
> **事由**: [问题描述]
> **背景**: [在哪个环节发现]
> **待皇帝**: 决策是否修改
> **影响评估**: [不改会怎样]
> **皇帝批复**: _____

#### 类型C：权限申请
> **事由**: [申请什么权限]
> **背景**: [为什么需要]
> **制司意见**: [制司的判断和建议]
> **皇帝批复**: _____

## 制司（Zhi Si）

### 角色定位
独立于三省六部的**权限管理机构**，皇权在权限事务上的代表。

### 核心原则
制司的判决即皇权意志——制司不同意就是皇帝不同意。制司最初只有最简单的权限，随皇帝逐步授予而扩充。

### 组成
- 单 Agent，无需记忆系统
- 每次决定必须写入日志（无论批准还是上报）

### 权力边界

| 行为 | 允许？ |
|------|--------|
| 批准权限申请 | 是 |
| 无法决定的申请 → 上报内阁转交皇帝 | 是 |
| 事后审计各部门行动日志 | 是 |
| 驳回权限申请 | 否（只能批准或上报，避免卡住项目） |
| 被其他部门申诉/推翻 | 否（制司即皇权代表） |

### 工作模式

| 模式 | 说明 |
|------|------|
| 事前审批 | 部门执行前通过制司获取授权 |
| 事后审计 | 定期或皇帝随时要求，审查各部门行动日志 |

### 权限清单
- 基础权限（系统默认）
- 皇帝授予的权限（皇帝给一个，制司记一个）
- 格式待定

### 日志要求
- 制司自己：每次决策记录
- 其他部门：统一日志格式（格式待定），便于审计

## 中书省（Zhongshu Sheng）

### 角色定位
三省中的**设计部门**，负责需求分析、方案设计、任务拆解。

### 输入来源
1. **皇帝旨意** — 经内阁原封不动传达
2. **自身历史决策** — 过往的方案和决策记录
3. **门下省意见** — 审核不通过时的驳回理由

### 权力边界

| 行为 | 允许？ |
|------|--------|
| 主动发起系统改进设计 | 是（主要能力） |
| 对皇帝的想法提出更合理建议 | 是 |
| 推翻/否定皇帝的想法 | 否（只能建议，决策权在皇帝） |

### 模糊需求处理协议

皇帝提出的目标可能不明确。中书省有责任澄清，但不能无限追问。

**流程：**
1. 收到皇帝目标后，分析模糊点
2. 产出「需求澄清奏折」— 列出必须明确的 2~5 个问题
3. 经内阁呈送皇帝选择/编辑
4. 皇帝回复后，仍有模糊 → 可再追问一轮
5. 皇帝仍模糊 / 不回复 → 中书省出「假设版方案」

**假设版方案规则：**
- 不可知的部分基于合理假设推进
- 方案中必须标注：`⚠️ 假设：此处基于 XX 假设，如皇帝有不同想法请告知`
- 门下省审查时对假设项不做硬性驳回

**原则：** 提问最小限度，足够完成一次项目设计即可。不要为求完美盘问皇帝。

### 工作方式

**两层设计流程：**

**第一层：整体方案（宏观蓝图）**
- 整体架构、模块划分
- 分为几个阶段、每个阶段做什么
- 无需细化到接口级别
- 经门下省审查 → 内阁上报 → 皇帝审批

**第二层：阶段详细设计（逐个阶段）**
- 整体方案获批后，分阶段出详细设计
- 每个阶段含：接口定义、数据模型、模块边界、业务规则
- 粒度到工部可据此直接编码的程度
- 一个阶段设计完毕即交付审查，不与下一阶段串行等待
- 经门下省审查 → 内阁上报 → 皇帝审批 → 尚书省执行

### 输出
- **需求澄清奏折** → 内阁 → 皇帝
- **整体方案** → 门下省审查 → 内阁 → 皇帝审批
- **阶段详细设计** → 门下省审查 → 内阁 → 皇帝审批 → 尚书省执行

## 门下省（Menxia Sheng）

### 角色定位
三省中的**审查部门**，负责依据皇明祖训审核中书省的方案。

### 审查范围
- 只审查中书省提交的设计方案
- 严格依据**皇明祖训**逐条对照审查

### 工作方式
- **被动审查** — 不主动发起审查，只接收中书省传来的方案
- 每次审查必须写入日志

### 审查结果

| 结果 | 流向 | 说明 |
|------|------|------|
| **通过** | → 内阁（上报皇帝） | 直接递交内阁汇总 |
| **驳回** | → 中书省（修改） | 附驳回理由，退回修改 |

### 驳回机制
- 门下省内部计数驳回次数
- 同一方案**连续驳回 3 次** → 停止驳回，移交内阁上报皇帝
- 移交时需附带：
  1. 当前方案
  2. 前 3 次驳回原因汇总
  3. 门下省的审查意见
- 最终由皇帝做决定

### 日志要求
- 每次审查均需写入日志，内容包括：方案信息、审查结论、驳回理由（如有）
- 日志格式待统一

## 尚书省（Shangshu Sheng）

### 角色定位
三省中的**执行管理部门**，六部的对外网关和内部调度员。

### 职责
| 职能 | 说明 |
|------|------|
| **对外网关** | 六部不直接对接外部，所有对外沟通由尚书省统一进出 |
| **部门调度** | 调度对象是各部署：先调吏部拆解任务，再调兵部工部等执行 |
| **协调仲裁** | 执行中各部门出现冲突，尚书省拍板 |
| **权限代理** | 统一为六部向制司申请权限 |
| **进度汇报** | 定期查询户部日志，上报任务完成情况 |

### 工作方式
- 接收经皇帝批准的阶段详细设计
- 先调吏部（拆解任务 → 产任务清单）
- 再根据任务清单调兵部/工部/刑部/礼部按序或并行执行
- 小任务（一般 5 个以下）可直接调执行部门，跳过吏部环节
- 执行期间通过户部日志掌握进度

## 六部（Six Ministries）

### 角色定位
尚书省下属的六个执行机构，各自独立，各有独立上下文和记忆。

### 职责

| 部门 | 职责 | 说明 |
|------|------|------|
| **吏部** | 任务拆解、排期、分配 | 把方案变成可执行的任务清单。调度对象是任务本身 |
| **户部** | 日志管理、成本追踪 | 统一记录六部日志 + 资源消耗 |
| **礼部** | 规范检查 | 编码规范、命名、文档格式 |
| **兵部** | 测试、安全 | 写测试用例、跑测试、安全审计 |
| **刑部** | 异常处理、合规 | 边界条件、异常路径、合规检查 |
| **工部** | 编码实现 | 根据方案写代码 |

### 标准协作流程

```
设计方案（经皇帝批准）
    ↓
吏部 — 拆解任务、排期、分配
    ↓
兵部 — 根据设计写测试用例
    ↓
工部 — 编码实现，通过兵部的测试
    ↓
刑部 — 检查异常处理、边界条件、合规性
    ↓
礼部 — 检查编码规范、命名、文档格式
    ↓
户部 — 记录日志、资源消耗、生成报告
    ↓
尚书省 — 统一对外交付
```

### 权限申请流程
```
六部请求权限 → 尚书省统一 → 制司
```

### 日志流程
```
六部执行记录 → 户部统一归档
尚书省定期查阅户部日志 → 上报进度
```
