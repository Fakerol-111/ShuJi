# 已知短板与改进方向

> 2026-05-13 · 当前为 PoC / 原型阶段

## 1. 测试闭环（当前最弱·已明确方案·待实施）

### 现状问题

兵部写测试代码靠"猜"环境，没有实际反馈循环。测试代码和产品代码由两个不同的 LLM 写，签名对不齐是常态，两边都在猜。刑部跑测试失败后分析原因经常误判，路由到错误部门。

### 新方案：契约驱动 + 同源测试

```
兵部 → 只产出接口契约（ctrt）：签名、类型、返回值结构、边界行为。不写一行代码。
工部 → 拿着契约写产品代码 + 测试代码。同一个 LLM，签名天然对齐。
刑部 → 创建环境 + 跑测试 + 贴原始 pass/fail 输出到 report。不做根因分析。
礼部 → 扩展职责：对照契约文档，检查测试是否覆盖了所有签名和边界条件。
```

### 为什么不会""作弊""

工部自己写测试自己写实现，理论上可以写 `assert True` 糊弄。但有三重约束：

1. **契约是顶棚** — 兵部定义了"函数叫什么、入什么、出什么、边界行为"。测试必须覆盖契约列出的所有签名。工部绕不过
2. **刑部暴露** — 测试原始输出贴在 report 里。尚书令或人能扫一眼：契约说 5 个函数，test name 只有 3 个 → 立刻发现覆盖不足
3. **礼部审计** — 礼部新增职责：对照契约检查测试覆盖的充分性。测试充足性的审计是独立第三方，不是工部自己

### 职责对比

| 部门 | 旧职责 | 新职责 |
|------|--------|--------|
| 兵部 | 写测试代码 + 写契约 + 创建环境 | **只写契约文档（ctrt）** |
| 工部 | 写产品代码 | **写产品代码 + 写测试代码** |
| 刑部 | 跑测试 + 分析失败原因 | **只跑测试 + 贴原始输出** |
| 礼部 | 规范检查 | **规范检查 + 测试覆盖审计** |

### 实施待办

- [ ] 兵部：移除文件写入工具，只保留文档工具 + read_file，prompt 重写为契约定义
- [ ] 工部：增加测试文件写入权限，prompt 增加"同时写测试代码"的 Deliver 要求
- [ ] 刑部：移除分析职责，prompt 简化为环境准备 + pytest 执行 + 输出贴 report
- [ ] 礼部：prompt 增加"对照契约检查测试覆盖充分性"的检查项

## 2. 错误恢复路径

**现状**：修完 bug 后的重验链靠尚书令 prompt 约束（soft constraint）。尚书令需要记住"礼部发现的问题 → 工部修完 → 回来重验礼部 → 再跑刑部"，出错时会遗漏步骤。

**改进方向**：

- 短期够用：尚书令 prompt 已有明确的 re-check 规则
- 如果未来任务量大了，需要硬状态机替代 prompt 约束
- 或在文档 YAML frontmatter 里记录"上次失败节点"，尚书令读取后自动从该节点恢复

## 3. 单任务单流水线

**现状**：当前设计假设一个项目一个任务串行执行。并行任务、跨模块依赖暂不支持，但现有架构不需要推翻。

**改进方向**：

- 需要时可扩展为多流水线并行，每个流水线独立 `.shuji/` 状态


- 跨模块依赖通过引用文档 ID（refs 字段）表达，已预留机制

## 4. 执行环境容器化（远期·已明确方向·暂不实施）

### 动机

LLM + shell 的组合在环境准备上极度脆弱。`pip install` 可能因网络、平台差异、版本冲突等原因失败，且 LLM 不擅长诊断环境问题。

### 方向

Docker / podman 容器化执行。每个任务启动时创建干净容器，依赖在容器内安装，测试在容器内运行，完成后销毁。解决：

- **隔离性** — 测试代码不接触宿主机，安全边界清晰
- **可复现** — 每次从干净起点开始，消灭"我机器上能跑"
- **可废弃** — 跑完即焚，不留残留状态

### 前置条件

- 测试闭环（第 1 节）的职责分工先落地跑通一个正式任务
- 之后再引入容器化加固执行环境
