# 系统文档约定

## 一、为什么要约定一个固定的文档格式

1. 针对多 agent 系统，对齐不同 agent 之间的颗粒度，让信息沟通更为完整，确保下游 agent 能完整得知自己要做什么，同时减少 prompt 的复杂度。
2. 让软件设计工程可视化、可审计化、可控。

## 二、文档定位

**文档系统只服务于部门间通信，与实际的源代码完全分开。**

```
.shuji/  ← 结构化文档体系（部门间通信用，走 create_document + write_document）
src/     ← 实际代码（走 write_file / edit_file / delete_file）
tests/   ← 测试代码（走 write_file / edit_file）
```

- 中书系、门下系、尚书令、内阁：只接触文档系统，无编码工具
- 兵部：写测试代码（write_file）+ 写文档（create_document）
- 工部：写源代码（write_file / edit_file），只读文档（read_file）
- 刑部/礼部：执行测试/检查 + 写文档报告（create_document）

## 三、文档功能

1. **命令** — 上游 agent 告知下游 agent 应当进行什么任务
2. **汇报** — 下级 agent 告知上级 agent 当前工作情况

## 四、文档设计

### 4.1 目录结构

```
.shuji/
├── designs/           # 整体设计方案、阶段方案（dsgn / plan / pdsg）
│   └── detail/        # 详细设计方案（ddtl）
├── reviews/           # 审查报告（revw）
├── tasks/             # 任务安排（task）
├── contracts/         # 接口契约（ctrt）
├── reports/           # 测试/规范报告（rprt）
├── logs/              # 运行日志（程序自动写入）
└── state.json         # 项目持久化状态
```

### 4.2 文档类型表

| 类型 | 前缀 | 目录 | 状态机 | 创建者 | 使用者 |
|------|------|------|--------|--------|--------|
| 整体设计 | `dsgn` | `designs/` | draft → approved → closed | 中书令 | 门下侍中 |
| 阶段规划 | `plan` | `designs/` | draft → approved → closed | 中书侍郎 | 内阁 |
| 阶段设计 | `pdsg` | `designs/` | draft → approved → closed | 中书侍郎 | 门下给事中，吏部 |
| 详细设计 | `ddtl` | `designs/detail/` | todo → done | 吏部尚书 | 兵部，工部 |
| 审查报告 | `revw` | `reviews/` | toread → done | 门下侍中/给事中 | 内阁 |
| 任务安排 | `task` | `tasks/` | todo → done | 尚书令 | 吏/兵/工/刑/礼部 |
| 接口契约 | `ctrt` | `contracts/` | todo → done | 兵部尚书 | 工部 |
| 测试报告 | `rprt` | `reports/` | todo → done | 刑部/礼部尚书 | 尚书令，内阁 |
| 项目总结 | `summary` | `designs/` | 无状态 | 内阁（专用工具） | 皇帝 |

### 4.3 文档内含字段

每条文档包含以下字段（YAML frontmatter，由程序自动组装）：

```yaml
---
id: dsgn_001
type: dsgn
status: draft
author: 中书令
timestamp: 2026-05-12T10:30:00
refs: [task_001]
---
文档内容主体……
```

| 字段 | 必填 | 说明 |
|------|------|------|
| `id` | 是 | 全局 ID，格式 `{type_prefix}_{序号}`，从全局计数器分配 |
| `type` | 是 | 文档类型前缀 |
| `status` | 是 | 当前状态 |
| `author` | 是 | 写作部门角色名 |
| `timestamp` | 是 | ISO 8601 格式 |
| `refs` | 是 | 引用文档 ID 列表，无引用则为 `[-1]` |
| `content` | 是 | 文档正文，由 LLM 生成 |

### 4.4 命名规则

文件名 = `{type_prefix}_{序号}.md`，**状态不体现在文件名中**。

示例：
- `dsgn_001.md`
- `ddtl_002.md`
- `task_005.md`

## 五、工具分层

### 5.1 按角色分配的工具集

| 角色 | 文档工具 | 编码工具 |
|------|----------|----------|
| 中书令 | `create_document` + `write_document` + `read_file` | 无 |
| 中书侍郎 | `create_document` + `write_document` + `read_file` | 无 |
| 门下侍中 | `read_file` + 决策关键词 | 无 |
| 门下给事中 | `read_file` + 决策关键词 | 无 |
| 内阁 | `summarize_project` + `read_file` + 决策关键词 | 无 |
| 尚书令 | `create_document` + `write_document` + `read_file` | 无 |
| 吏部尚书 | `create_document` + `write_document` + `read_file` | 无 |
| 兵部尚书 | `create_document` + `write_document` + `read_file` | `write_file`（测试代码） |
| 工部尚书 | `read_file` | `write_file`/`edit_file`/`execute_command` |
| 刑部尚书 | `create_document` + `write_document` + `read_file` | `execute_command` |
| 礼部尚书 | `create_document` + `write_document` + `read_file` | 无 |

### 5.2 文档元数据操作

#### create_document

创建一个新文档。程序分配 ID，组装 YAML 头，写入文件。

```
create_document(
    type: "dsgn" | "plan" | "pdsg" | "ddtl" | "task" | "ctrt" | "rprt" | "revw",
    refs: number[],         // 引用文档 ID，无引用传 [-1]
    // status、author 由程序自动设置：
    //   dsgn/plan/pdsg → draft
    //   ddtl/task/ctrt/rprt → todo
    //   author → 当前角色
)
```

返回：`{type_prefix}_{id}`（如 `dsgn_003`）

#### set_document_status

显式更新文档状态。与 `<decision>` 关键词互补：
- **主动调用**：LLM 认为需要变更状态时直接调此工具
- **被动拦截**：`<decision>approve/reject</decision>` 由程序自动截获处理

```
set_document_status(
    id: string,          // 文档 ID，如 "dsgn_003"
    status: string       // 目标状态
)
```

### 5.3 文档内容操作

文档的内容编辑与文件工具类似，但操作对象是已注册的文档（通过 ID 而非路径定位），且只操作 YAML header 之后的正文部分，不破坏结构化头。

```
write_document(id, content)    // 写入正文，覆盖已有内容
edit_document(id, old, new)    // 替换正文中的指定文本
append_document(id, content)   // 在正文末尾追加内容
```

编辑流程示例：LLM 先 `create_document` 拿到 ID，再多次 `write_document`/`append_document` 填写正文。

### 5.4 summarize_project（内阁专用）

读取项目当前所有文档的头部摘要，拼接后让 LLM 填充分析。

```
summarize_project()
    // 无参数
```

程序行为：
1. 收集近期所有文档的头部信息（id/type/status/author/timestamp）
2. 按时间排序，拼成摘要
3. 让 LLM 填充分析内容
4. 组装 summary 文档返回

### 5.5 决策关键词

门下侍中/给事中的输出会被程序扫描。当包含特定关键词时，程序自动更新对应文档的 `status`：

```
<decision>approve</decision>   → 更新文档 status = approved
<decision>reject</decision>    → 更新文档 status = draft（退回修改）
```

例如门下侍中审查 `dsgn_003` 后输出全文如下，程序截获 `approve` 后更新 `dsgn_003.md` 的 `status`：

```
<decision>approve</decision>
整体设计合理，技术选型符合要求。
route_to(to="内阁", subject="dsgn_003")
```

审查意见如需保留，LLM 可以在输出正文中写下评语；程序截获 `<decision>` 时不会改动正文内容。

## 六、完整流转示例

### 6.1 设计方案流转

```
1. 皇帝 → 内阁："设计 JWT 认证模块"
2. 内阁：
   summarize_project()  ← 程序收集上下文
   route_to(to="中书令", subject="task_001")
       # task_001.md 由 内阁 的任务分发逻辑创建（或由程序预创建）

3. 中书令 收到通知，读 task_001，然后：
   create_document(type="dsgn", refs=[1])       → 返回 dsgn_002
   write_document(id="dsgn_002", content="## 整体设计\n...")
   route_to(to="门下侍中", subject="dsgn_002")

4. 门下侍中 收到通知，读 dsgn_002.md，审查后输出：
   <decision>approve</decision>
   方案可行。
   route_to(to="内阁", subject="dsgn_002")
       → 程序检测 approve，dsgn_002.md status → approved

5. 内阁 看到 dsgn_002 status=approved：
   summarize_project()
   呈报皇帝
```

### 6.2 执行阶段流转

```
1. 尚书令 收到批准后的 dsgn_002：
   create_document(type="task", refs=[2])       → 返回 task_003
   write_document(id="task_003", content="请完成 JWT 认证模块详细设计")
   route_to(to="吏部尚书", subject="task_003")

2. 吏部尚书 完成任务后：
   create_document(type="ddtl", refs=[3, 2])    → 返回 ddtl_001
   write_document(id="ddtl_001", content="## JWT 模块设计\n...")
   route_to(to="尚书令", subject="ddtl_001")

3. 尚书令 继续调度（兵部写测试、工部编码、刑部验证……）
```

## 七、实现要点

### 7.1 ID 生成器

全局单调递增计数器，进程内用 `tokio::sync::Mutex` 保护：

```
文件名: .shuji/_counter
内容: {"next_id": 1}
```

每次 `create_document` 调用时：
1. 锁计数器
2. 读取当前值
3. 写入 `next_id + 1`
4. 释放锁
5. 用读取的 ID 生成文档

### 7.2 目录初始化

每次项目打开时，系统自动调用 `ShujiDir::init()` 创建以下目录（已有则跳过）：

```
.shuji/designs/detail/
.shuji/reviews/
.shuji/tasks/
.shuji/contracts/
.shuji/reports/
.shuji/logs/
```

同时检查 `.shuji/_counter` 是否存在，不存在则创建并初始化为 `{"next_id": 1}`。

### 7.2 决策关键词截获位置

在 `AgentController`（control.rs）或 `Actor`（actor/mod.rs）的输出处理层，扫描 LLM 返回文本中的 `<decision>...</decision>` 标签：
- 匹配时：调用文档状态更新函数，改写对应文档 YAML 头中的 `status`
- 不匹配时：不做额外操作

### 7.3 document 与 route_to 的关联

`route_to` 的 `subject` 直接传文档 ID，接收方通过 `read_file` 读取对应文档：
```
route_to(to="门下侍中", subject="dsgn_002")
    → 门下侍中 read_file("designs/dsgn_002.md")
```

## 八、工具实现设计

### 8.1 总体架构

文档工具作为新的工具层，与现有的文件工具（`read_file`/`write_file`）平级，共享同一个调度入口 `execute_named_tool`。

```
execute_named_tool(tool_name, args)
  ├── read_file / write_file / edit_file …   ← 现有文件工具
  ├── create_document / write_document …      ← 新增文档工具（8.2-8.4）
  └── route_to                                ← 路由工具（现有）
```

文档工具的实现在新的文件 `tool/documents.rs` 中，每个工具一个异步函数，通过 `tool/mod.rs` 中的 `execute_named_tool` 分发。

### 8.2 create_document

**工具定义：**
```json
{
    "name": "create_document",
    "description": "创建一个新文档，返回文档 ID",
    "input_schema": {
        "type": "object",
        "properties": {
            "type": {
                "type": "string",
                "enum": ["dsgn", "plan", "pdsg", "ddtl", "task", "ctrt", "rprt", "revw"]
            },
            "refs": {
                "type": "array",
                "items": {"type": "integer"}
            }
        },
        "required": ["type", "refs"]
    }
}
```

**程序行为：**

```
create_document(type, refs):
  1. 校验 type 在合法列表中
  2. 加锁全局计数器，读取 next_id，写入 next_id + 1，解锁
  3. 确定初始 status：
     dsgn/plan/pdsg → "draft"
     ddtl/task/ctrt/rprt/revw → "todo"
  4. 确定 author：从当前调用角色获取
  5. 组装文档 ID："{type}_{next_id}"
  6. 写入文件 ".shuji/{dir}/{id}.md"：
     ---
     id: {id}
     type: {type}
     status: {status}
     author: {author}
     timestamp: {ISO 8601}
     refs: {refs}
     ---
     （空正文占位）
  7. 返回 id（字符串）
```

**目录映射：**
| type | dir |
|------|-----|
| dsgn/plan/pdsg | `designs/` |
| ddtl | `designs/detail/` |
| revw | `reviews/` |
| task | `tasks/` |
| ctrt | `contracts/` |
| rprt | `reports/` |

**错误处理：**
- `type` 不合法 → 返回错误信息
- `refs` 包含非数字 → 过滤非数字项，继续执行
- 文件写入失败 → 返回 IO 错误

### 8.3 文档内容工具

三个工具共享同一套 YAML frontmatter 解析逻辑：

```
read_doc(path) → (header: YAML, body_start: usize, body_end: usize)
```

具体步骤：
1. 从文件第一行开始，查找 `---` 分隔符
2. 找到第一个 `---`，继续查找第二个 `---`
3. 两个 `---` 之间的内容为 YAML header，用 `serde_yaml` 或 `serde_json` 解析
4. 第二个 `---` 之后的内容为正文
5. 返回 header + 正文的起止位置

#### write_document

```
write_document(id, content)
```

1. 根据 `id` 解析出文件路径（如 `dsgn_003` → `.shuji/designs/dsgn_003.md`）
2. 读文件
3. 解析 YAML frontmatter，找到正文起止位置
4. 用 `content` 替换第二个 `---` 之后的内容
5. 更新 `timestamp` 字段
6. 写回文件
7. 成功返回空，失败返回错误

#### append_document

```
append_document(id, content)
```

1. 同 `write_document` 读文件 + 解析 frontmatter
2. 在正文末尾追加 `content`
3. 更新 `timestamp`
4. 写回文件

#### edit_document

```
edit_document(id, old, new)
```

1. 读文件 + 解析 frontmatter
2. 在正文中查找第一个 `old` 精确匹配
3. 替换为 `new`
4. 更新 `timestamp`
5. 写回文件
6. 未找到匹配时返回错误提示

**约束：**
- 三个工具都只修改第二个 `---` 后面的正文区域，YAML header 由程序维护，LLM 不能直接修改
- `edit_document` 每次只替换第一个匹配，需要多出替换时多次调用

### 8.4 set_document_status

```
set_document_status(id, status)
```

1. 根据 `id` 定位文件
2. 读文件，解析 YAML frontmatter
3. 校验 `status` 是否符合当前类型的合法状态迁移：
   - dsgn/plan/pdsg: draft → approved → closed 或 draft → draft（reject）
   - ddtl/task/ctrt/rprt/revw: todo → done
4. 更新 YAML 中的 `status` 和 `timestamp`
5. 写回文件
6. 非法状态迁移返回错误

### 8.5 决策关键词拦截

**拦截位置：** `AgentController` 的 `run()` 循环中，LLM 返回文本后、返回 `AgentOutput` 之前。

**拦截逻辑：**

```
1. 扫描 output_text 中的 <decision>...</decision>
2. 如果找到：
   a. 提取 decision 内容（approve/reject）
   b. 从后续的 route_to subject 中提取文档 ID
   c. 调用 set_document_status(id, decision_to_status)
3. 从 output_text 中移除 <decision> 标签，不留在发给前端的内容中
```

**状态映射：**
```
approve → approved（对应 dsgn/plan/pdsg）
reject → draft（退回修改）
```

**示例：**

LLM 输出：
```
<decision>approve</decision>
整体设计合理。
route_to(to="内阁", subject="dsgn_003")
```

程序处理：
1. 截获 `<decision>approve</decision>`
2. 解析后续 `route_to` → subject="dsgn_003"
3. 调用 `set_document_status("dsgn_003", "approved")`
4. 从文本中移除 `<decision>approve</decision>`
5. 最终发给前端的内容：`整体设计合理。`

**注意：** 如果 LLM 同时输出多个 `<decision>`，只处理第一个；多个 `route_to`，取第一个 route_to 的 subject。

### 8.6 summarize_project（内阁专用）

独立工具，不同于通用文档工具。在内阁 Agent 的工具列表中注册。

```
summarize_project()
```

程序行为：
1. 遍历 `.shuji/designs/`、`.shuji/reviews/`、`.shuji/tasks/`、`.shuji/contracts/`、`.shuji/reports/`
2. 对每个文档，读取 YAML header，提取 (id, type, status, author, timestamp)
3. 按 timestamp 排序
4. 拼接成以下格式的摘要文本：

```
## 项目文档摘要

### designs/
- dsgn_001 | approved | 中书令 | 2026-05-12T10:00
- dsgn_002 | draft   | 中书令 | 2026-05-12T11:00

### reviews/
- revw_001 | done | 门下侍中 | 2026-05-12T10:30

### tasks/
- task_001 | done | 尚书令 | 2026-05-12T09:00
- task_002 | todo | 尚书令 | 2026-05-12T11:30
```

5. 将摘要文本作为上下文传给 LLM，让 LLM 填充分析
6. LLM 输出分析内容后，程序组装 summary 文档写入 `.shuji/designs/summary_{timestamp}.md`

### 8.7 文件结构变更

```
src-tauri/src/tool/
├── mod.rs          ← 现有，加入新工具的注册和分发
└── documents.rs    ← 新增，文档工具实现
```

`tool/mod.rs` 的变更：
- 新增 `documents.rs` 模块声明
- 在工具定义函数中增加文档工具的定义
- 在 `execute_named_tool` 中增加文档工具的分发分支
