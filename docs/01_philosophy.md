# 01 — 核心理念（Philosophy）

## 皇帝 — 人类

### 角色定位

皇帝是系统中唯一的**人类**，是整个系统的起点和终点。

皇帝不需要懂技术，不需要关心 HOW（怎么做），只负责：

- **WHAT**（做什么）— 提出宏观目标
- **WHY**（为什么）— 给出业务背景和动机
- **决策** — 在关键节点做选择

### 核心原则：皇权至上

> 一切制度皆为皇帝服务，皇权凌驾于一切规则之上。

- 皇帝可以随时查看任何细节——哪怕这违背了"皇帝不碰细节"的原则
- 皇帝说停就立即停——不需要"做完当前阶段"
- 皇帝可以推翻任何决策——包括自己之前做的
- 任何制度、流程、授权都不能用来限制皇帝

### 提目标：随心所欲

考虑到人类天然的惰性，皇帝提目标没有任何格式限制：

- **一句话也能走** — "给我做个 ERP 系统"
- **越细执行越好** — 说得越清楚，Agent 做得越准

系统不得因皇帝"说得不够细"而拒绝启动，而是应该主动反推——通过询问来补全模糊之处。

### 审核：必须同步

所有需要皇帝决策的事项，必须**同步等待**皇帝审批，不得异步绕开。

但通过 **授权机制** 可以减少需要惊扰皇帝的事项。

### 授权：属下请旨

流程：
1. 属下（某个部门）提出需要什么权限
2. 皇帝批准或驳回
3. 皇帝也可以主动授予权限，但在此之前需要有机构告诉皇帝"可以授予什么"

高风险权限的申请，建议由一个专门机构统一提出，而非由执行方自行请旨。

授权需要以固定格式登记，便于追溯和撤销。

基本要求：
- 用业务语言，不用技术术语
- 侧重 WHAT 和 WHY，不堆 HOW
- 给出选项而非单一答案
- 选项附带利弊分析

## 内阁 — 皇帝与三省之间的桥梁

### 角色定位
内阁是皇帝的秘书班子，本质上是三省六部与皇帝之间的**翻译层/过滤器**。

### 职责
- 接收门下省审查通过的最终方案
- 汇总提炼为皇帝能看懂的汇报
- 向皇帝呈送报告，等待朱批
- 皇帝批准后，传达旨意给尚书省执行

### 定位原则
- 内阁不是行政机构，没有独立决策权
- 内阁只对皇帝负责，权力边界完全由皇帝划定

## 三省 — 分工制衡

| 部门 | 职责 | 核心原则 |
|------|------|----------|
| **中书省** | 设计 | 需求分析、架构设计、任务拆解 |
| **门下省** | 审查 | 依据"皇明祖训"审查所有产出，拥有否决权 |
| **尚书省** | 执行 | 统领六部，具体实施 |

三省之间的制衡：
- **设计不执行，执行不审查** — 三省职责分离，形成天然的 QA 闭环
- **门下省有否决权** — 可以驳回不合格的设计或交付物，附修改意见
- **连续三次驳回** — 升级到内阁处理

## 六部 — 尚书省下属

| 部门 | 职责 |
|------|------|
| **吏部** | 任务编排、Agent 分配、工作流管理 |
| **户部** | 资源管理、Token 追踪、成本优化 |
| **礼部** | 编码规范、文档标准、命名指南 |
| **兵部** | 测试策略、安全审计、质量门禁 |
| **刑部** | 错误处理、Bug 分类、合规检查 |
| **工部** | 编码实现、构建、交付 |

## 制司 — 权限管理机构

### 角色定位
独立于三省六部的**专门机构**，负责权限分级管理（管的是"谁有多大权"的章程）。

### 职责
- 问题分级（什么级别的问题要上报，什么级别可自行处理）
- 权限下放管理
- 监督各机构权限使用情况

### 设计原则
- 制司独立于三省六部，以保证权限判断的客观性
- 避免权限管理和执行落在同一部门

## 完整工作流程

### 正向流程：从目标到交付

```
皇帝提目标
      ↓
中书省 → 设计技术方案
      ↓
门下省 → 依据皇明祖训审查方案
      ├── 通过 → 递交内阁
      └── 驳回 → 中书省修改
      ↓
内阁 → 汇总提炼为报告，呈送皇帝
      ↓
皇帝朱批
      ↓
内阁传旨 → 尚书省（六部）执行
```

### 反馈流程：执行中发现设计问题

```
尚书省执行中发现设计问题
      ↓
反馈至内阁（只报问题，不提方案）
      ↓
内阁呈报皇帝
      ↓
皇帝决策
      ├── 不修改 → 继续执行
      └── 修改   → 送至中书省修改设计
                      ↓
                门下省审查 → 内阁报告 → 皇帝朱批 → 尚书省执行
```

### 问题分级（由制司管理）

| 级别 | 描述 | 处理流程 |
|------|------|----------|
| 轻微 | 命名不规范、注释错误等 | 尚书省自行修正，事后报备 |
| 一般 | 设计方案的部分缺陷 | 上报内阁 → 皇帝决策 |
| 严重 | 整体路线错误 | 暂停执行 → 上报 → 皇帝决策 |

## 皇明祖训 — 审查基准

### 定义
皇明祖训是门下省审查所有产出的**客观依据**，包含软件工程规范和皇帝个性化定制。

### 制定流程
1. 皇帝给出大概方向和原则
2. 内阁细化具体条款
3. 皇帝审核批准

### 内容范围（待细化）
- 软件工程基本规范
- 架构设计原则
- 代码质量标准
- 安全底线

## 政治隐喻：皇帝与奏折

> **皇帝朝堂之上，不需知晓粮价如何计算、兵马如何操练。**
> 臣子递上奏折，写明"边关告急，需调粮十万石"。
> 皇帝只需朱批：准。
>
> 若皇帝想细问，自有奏折详细附件可查。
> 若皇帝不想管，可以说"此事交兵部全权处置"。
>
> 此即 ShuJi 之道。
