# 枢机（ShuJi）— 开题答辩用

> 基于中国古代三省六部制的 AI 驱动自动化软件开发系统
>
> 以下内容根据实际代码（2026-05-12）整理，适合 5 分钟 PPT 讲解。

---

## 一、开题背景与意义

### 背景

现有 AI 编程助手（如 Cursor、Copilot）主要解决"怎么写代码"的问题，但**软件开发流程的组织**仍然依赖人工。从需求分析 → 设计 → 审查 → 任务拆解 → 写测试 → 编码 → 验证 → 规范检查，这些环节的编排、角色分工和质量门禁，目前没有被系统化地交给 AI 处理。

### 三大痛点

| 痛点 | 说明 |
|------|------|
| **上下文混用** | 一个 LLM 会话承载所有角色，设计决策和编码细节混在一起 |
| **没有强制力** | AI 可以跳过步骤、不写日志，全靠自觉 |
| **缺乏制衡** | 没有职责隔离——设计者同时可以写代码，缺少质量门禁 |

### 意义

枢机将**中国古代三省六部制的治理智慧**映射到 AI 驱动的软件开发流程，让 AI Agent 各司其职、互相制衡，实现从需求到交付的全流程自动化。

---

## 二、项目目标

构建一个**基于 LLM Agent + 角色分工**的自动化软件开发桌面系统。

### 核心原则

- **皇帝（人类）**只提目标和做关键决策，不关心技术细节
- **内阁**通过 skill 系统动态选择工作流，路由任务到对应部门
- **职责隔离**——设计的不写代码，编码的不做审查
- **文档是契约**——部门间通过结构化文档通信，而非 LLM 对话传递上下文
- **流程自适应**——任务简单走轻量流程，复杂走全流程

### 关键特征

- 10 个独立 LLM Agent，各自维护独立上下文
- Actor 模型异步通信，支持并行执行
- 自动质量门禁（设计审查 → 测试验证 → 规范检查）
- 文档中心通信（YAML frontmatter + 自动 ID 分配）

## 三、开发技术路线

### 技术栈

| 层 | 技术 |
|------|------|
| 桌面框架 | Tauri v2（跨平台原生应用） |
| 后端语言 | Rust（tokio 异步运行时） |
| 前端框架 | React 19 + TypeScript |
| 构建工具 | Vite 6 |
| 样式 | Tailwind CSS v4 |
| LLM API | 双格式兼容：OpenAI / Anthropic |
| HTTP 客户端 | reqwest |

### 核心架构

```
皇帝 → send_message → 内阁(skill系统) → route_to → 各部门
  ├─ 中书令     — 系统设计
  ├─ 门下侍中   — 设计审查
  ├─ 尚书令     — 执行调度
  │   ├─ 吏部尚书   — 详细设计
  │   ├─ 兵部尚书   — 测试 + 接口契约
  │   ├─ 工部尚书   — 编码（含计划循环）
  │   ├─ 刑部尚书   — 测试验证
  │   └─ 礼部尚书   — 规范检查
  └─ 制司       — 权限管理
```

### 关键设计

| 设计 | 说明 |
|------|------|
| **Actor 模型** | 每个部门是独立的消息循环（actor），通过异步通道通信，互不阻塞、天然支持并行 |
| **Session / Controller 分离** | Session 只负责 LLM 一轮对话；Controller 负责 tool 循环、中断恢复和生命周期管理，各司其职 |
| **Skill 系统** | 内阁通过动态切换工作模式（轻量流程 / 标准流程 / 复杂流程 / 讨论 / 澄清等）来适配不同任务 |
| **文档中心通信** | 部门间通过 `.shuji/` 下的结构化文档（YAML frontmatter + 自动 ID）传递信息，而非靠 LLM 对话传递上下文 |
| **制衡机制** | 三省职责分离：设计的不审查、审查的不执行、执行的不设计；门下省拥有驳回权，形成天然质量门禁 |
| **流程自适应** | 任务简单走轻量流程（直接编码），复杂走全流程（设计→审查→批准→执行），不做一刀切 |

| **第 1 周** | 第 1-7 天 | Tauri 项目初始化、数据模型定义、Agent Trait + 各角色 Mock Agent 实现、Actor 系统（消息通道 + 路由）、存储层（.shuji/） | 单机可运行的原型，Mock Agent 全流程走通 |
