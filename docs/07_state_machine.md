# 07 — 项目状态机（State Machine）

> 定义项目从开始到结束的所有可能状态及流转规则。
> 每个项目维护一个 `state.json`，驱动工作流引擎。

## 状态定义

| 状态 | 说明 | 谁在处理 |
|------|------|---------|
| 目标已接收 | 皇帝提出目标，内阁已传达至中书省 | 中书省 |
| 需求澄清中 | 目标模糊，中书省正在追问皇帝 | 中书省 → 内阁 → 皇帝 |
| 需求已明确 | 皇帝回复，目标足够推进 | 中书省 |
| 整体方案设计中 | 中书省正在出整体方案 | 中书省 |
| 整体方案审查中 | 方案已交门下省审查 | 门下省 |
| 整体方案待批 | 审查通过，已交内阁上报皇帝 | 内阁 → 皇帝 |
| 整体方案驳回待改 | 被驳回，中书省修改中 | 中书省 |
| 整体方案驳回升级 | 连续 3 次驳回，皇帝决定 | 皇帝 |
| 整体方案已批准 | 皇帝批准，进入阶段设计 | 尚书省启动准备 |
| 阶段详细设计中 | 中书省出当前阶段详细设计 | 中书省 |
| 阶段设计审查中 | 门下省审查阶段设计 | 门下省 |
| 阶段设计待批 | 审查通过，等候皇帝批示 | 内阁 → 皇帝 |
| 阶段设计驳回待改 | 阶段设计被驳回 | 中书省 |
| 阶段设计驳回升级 | 连续 3 次驳回阶段设计 | 皇帝 |
| 阶段设计已批准 | 阶段设计获批，开始执行 | 尚书省 |
| 阶段执行中 | 尚书省组织六部执行 | 尚书省 + 六部 |
| 执行反馈中 | 发现问题，反馈至内阁 | 尚书省 → 内阁 |
| 执行轻微问题 | 制司判为轻微，自行修正中 | 尚书省 |
| 问题待皇帝决策 | 需皇帝决定改不改 | 内阁 → 皇帝 |
| 问题修改设计中 | 皇帝决定改，送回中书省改设计 | 中书省 |
| 执行阻塞 | 问题严重，执行暂停 | 尚书省 |
| 已交付 | 项目全部完成 | — |
| 已暂停 | 皇帝或流程要求暂停，可恢复 | — |
| 已终止 | 皇帝叫停，不可恢复 | — |

## 状态流转规则

### 规则 1：谁可以改变状态

| 状态变化 | 由谁触发 |
|---------|---------|
| 正常流程推进 | 当前处理部门完成工作后，更新状态并发起下一环节 |
| 驳回 | 门下省 |
| 升级 | 门下省（达到驳回上限） |
| 批准/驳回/暂停/终止 | 皇帝（通过内阁传达） |

### 规则 2：状态文件 `state.json`

每个项目的根目录下维护一个 `state.json`：

```json
{
  "project": "项目名",
  "goal": "皇帝原始目标",
  "state": "整体方案审查中",
  "currentPhase": null,
  "rejectCount": 0,
  "createdAt": "2026-05-07T10:00:00+08:00",
  "history": [
    { "at": "2026-05-07T10:00:00+08:00", "event": "皇帝提出目标", "actor": "皇帝", "from": null, "to": "目标已接收" },
    { "at": "2026-05-07T10:05:00+08:00", "event": "中书省开始设计整体方案", "actor": "中书省", "from": "目标已接收", "to": "整体方案设计中" }
  ]
}
```

### 规则 3：state.json 自动更新规则

- 每个部门完成工作后，将当前项目状态更新为下一状态
- 追加一条历史记录
- 状态变更后，工作流引擎判断下一步交给谁
